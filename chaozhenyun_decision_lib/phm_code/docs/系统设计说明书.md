# 多工况自适应工业设备控制优化系统 V1.0 系统设计说明书

## 一、设计目标

| 目标 | 具体要求 |
|---|---|
| 工况自适应 | 评估基准与优化上下文随工况自动切换，不使用全局固定阈值 |
| 多场景适配 | 换应用场景只换配置，内核代码不动 |
| 安全可控 | 任何写向现场的操作都经过不可绕过的安全关卡，失败可整体回滚 |
| 可解释 | 每条建议附带可逐条展开的证据链 |
| 可追溯 | 任意一次写值可回溯到原始数据与全部中间判断 |
| 可闭环 | 执行效果自动核验，验证有效的经验自动回流 |
| 低依赖 | 除 NumPy 外不引入第三方库，可在边缘网关部署 |

## 三、关键设计决策与理由

### 3.1 为什么按工况建立基线，而不是全局阈值

同一设备在不同负载下各测点的正常范围差异可达数倍。全局阈值必然在一端漏报、另一端误报。按工况建立基线的代价是需要为每个工况单独积累样本，投运初期有一段基线学习期；收益是误报率大幅下降，系统能被现场持续使用。这个取舍是值得的——工业软件的最大失败模式不是算得不准，而是误报太多导致被闲置。

### 3.2 为什么用轻量代理模型，而不是神经网络

现场可获得的运行样本通常只有几十到几百条，且分布集中在少数几个常用工作点附近。在这种样本条件下，参数量大的模型必然过拟合，且在无样本区域会给出任意外推结果。加权最近邻结合局部线性的模型在样本少时退化为最近邻、样本多时接近局部回归，并能输出可信的预测置信度——外推到无样本区域时置信度趋近零，上层据此拒绝该建议。这个"知道自己不知道"的能力，比预测精度更重要。

### 3.3 为什么把邻域限制写进算法而不是靠后置检查

工业参数调整必须小步走。如果让算法在全域寻优、再由安全门砍到限幅之内，得到的往往是"朝着远方最优点的方向走一小步"，而这个方向在局部未必是最优的。把邻域限制放进搜索空间，算法直接在允许范围内找局部最优，结果更可靠。安全门的限幅检查仍然保留，作为第二道保险。

### 3.4 为什么效果评估必须做显著性检验

工业过程本身有波动。若只比较调整前后的均值，工况的自然漂移会被误判为调整效果，系统会"学到"错误的经验，并且会越学越偏。Welch t 检验（不假设方差齐性）能把"变化幅度相对于波动是否足够大"量化出来。未通过检验的变化会被打折计入奖励，而不是直接丢弃——因为多次不显著的同向变化，累积起来仍然携带信息。

### 3.5 为什么奖励函数对负向变化加重惩罚

"省了电但设备更抖"这类拆东墙补西墙的调整，如果按对称权重计算，可能得到接近零的奖励，系统就学不会避开它。加重负向惩罚（默认 1.5 倍）使系统在收益与风险之间保守偏移，符合工业场景"宁可少省一点，不可增加故障风险"的实际偏好。

### 3.6 为什么审计账本用链式哈希

工业控制系统的写值记录可能涉及事故责任认定。普通日志可以被编辑而不留痕迹。链式哈希（每条记录含前序哈希）使得任何一条记录被篡改或删除，都会导致其后所有记录的校验失败，且无法在不重算全链的情况下伪造。系统提供独立的校验命令，可随时验证账本完整性。

### 3.7 为什么只改设定值不接管调节回路

现场 PLC/DCS 内部的 PID、联锁与保护逻辑是设备安全运行的最后防线，经过长期验证。上位系统接管这些逻辑意味着把安全责任转移到一个刚上线的软件上，风险极高且现场不会接受。只写设定值的策略把系统定位为"给控制系统提建议的顾问"，即使系统完全失效，设备仍在原有控制逻辑下正常运行。

```
   ▼

   │                                      │
   │  ③五道清洗                            ├──▶ TimeSeriesBuffer（供效果评估取窗口）
   ▼                                      │
CleansingReport                            ▼
                                    ④FeatureExtractor
                                           │
                                           ▼
                                    FeatureVector
                                     │          │
                          ⑤工况识别   │          │  ⑥健康评估
                                     ▼          ▼
                          ConditionSnapshot  HealthReport
                                     └────┬─────┘
                                          ▼
                                  ⑦OptimizationAdvisor
                          （知识推理 + 案例复用 + 代理模型寻优）
                                          ▼
                                 OptimizationAdvice

                                          ▼

                        ▼          ▼             ▼          ▼
                    代理模型    规则可信度      案例库    工况档案
```

## 五、并发与线程模型

| 组件 | 线程模型 |
|---|---|
| 调度器 | 单线程执行，保证同一时刻只有一个任务在跑，避免共享状态竞态 |
| 事件总线 | 同步模式（确定性，便于测试）与异步模式（多工作线程，高吞吐）可切换 |
| 采集驱动 | 每个驱动内部加锁，支持多线程调用 |
| 时序缓冲 | 可重入锁保护，写入路径尽量短 |
| 控制执行 | 全程加锁串行，杜绝并发写同一设备 |
| HTTP 服务 | 多线程服务器，业务逻辑委托给引擎（引擎内部已加锁） |

## 六、扩展点

| 扩展需求 | 做法 |
|---|---|
| 新增通信协议 | 继承 `ProtocolDriver` 实现四个方法，用装饰器注册到 `DRIVER_REGISTRY` |
| 新增控制系统类型 | 继承 `ControlAdapter` 实现读写方法，注册到 `CONTROL_ADAPTER_REGISTRY` |
| 新增寻优算法 | 继承 `BaseOptimizer` 实现 `optimize`，注册到 `OPTIMIZER_REGISTRY` |
| 新增故障判据 | 追加 `PatternRule` |
| 新增业务规则 | 编辑规则 JSON 文件或追加 `Rule` |
| 新增应用场景 | 编写 `ScenarioProfile` 并注册到场景表 |
| 更换存储介质 | 实现与 `FileRepository` 同接口的类 |

以上扩展均不需要修改引擎代码。

## 七、测试设计

| 测试文件 | 覆盖内容 |
|---|---|
| `tests/test_core_and_acquisition.py` | 配置校验与脱敏、事件总线故障隔离、审计链篡改检出、Modbus 编解码往返、缓冲窗口与保留期、五道清洗（含设定值不误判死值） |
| `tests/test_analysis_and_knowledge.py` | 时域特征（正弦有效值、高斯峭度、冲击信号）、频域特征（主频定位、轴承特征频率关系）、工况识别（同工况不重复新建、稳态判定）、基线偏离、规则推理（前向链、缺失事实、注入拒绝）、约束、案例检索与修正 |
| `tests/test_optimize_control_feedback.py` | 搜索空间归一化与邻域限制、代理模型趋势与置信度、三种算法收敛与可复现、调整表达式解析、安全门七道检查逐项、奖励非对称性与显著性折扣、端到端闭环、故障注入检出 |

关键回归点：工况库失控（同工况被反复新建）在 `test_same_condition_is_not_recreated` 与端到端测试中双重设防，因为这个缺陷会连锁导致基线建不起来、健康度恒为满分、优化与反馈全部空转。
